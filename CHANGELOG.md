# Changelog

One line per significant chunk of work, newest first.

- 2026-07-25: Refactored Odoo connection onboarding into a staged, archive-safe flow. `TenantOdooCredential` gained a `state` machine (draft → active, via `POST .../credentials` for initial setup and `PUT .../credentials/company` as the activation step; a distinct `POST .../credentials/reauthenticate`, only usable once active, replaces the old dual-purpose save form); a new `require_active_instance` gate blocks every Odoo-talking endpoint (Operation Types/Warehouses refresh, Vehicle/Driver Odoo browse + link) with a 409 until setup completes — Vehicle/Driver core CRUD and unlink stay ungated, preserving the earlier "locally-owned" decision. "Resync List" is now preview-then-confirm: a new `POST .../refresh/preview` diffs against Odoo without writing (`{new, removed, unchanged_count}`), and the frontend shows this before the existing confirm-and-apply call runs. Added an `active` archive/soft-delete flag (Odoo-style convention) to `SyncedOperationType`, `SyncedWarehouse`, `Vehicle`, and `Driver` — new archive-toggle endpoints for the first two, extended the existing update endpoint for the other two, plus new `include_archived` list filtering and new `DELETE` endpoints for Operation Types/Warehouses (didn't exist before) that block with an "archive instead" message when referenced (by a synced picking, or, for warehouses, a vehicle's home warehouse). Frontend: Connection page reworked into explicit Test → Save → Load companies → Activate steps with a distinct Re-authenticate action once active; Operation Types/Warehouses pages gated behind an active connection with a link back to Connection; Vehicles/Drivers pages always usable, with the Odoo-link picker replaced by an inline note when not active. 117 backend tests passing (29 new), ruff/eslint/tsc all clean. Verified end-to-end against the real Odoo instance: the migration's backward-compat step correctly auto-activated the existing pre-batch connection (it already had a company selected); preview correctly diffed real operation-type/warehouse data scoped to the selected company (86 previously-synced rows vs. 14 unchanged/72 no-longer-in-scope after switching company scope, confirming the diff isn't a no-op); confirm-refresh updated `last_synced_operation_types_at`/`last_synced_warehouses_at`; archive/unarchive round-tripped and correctly changed default vs. `include_archived=true` list counts; the warehouse delete guard correctly blocked (400) deleting a warehouse referenced by a live-created vehicle's `home_warehouse_id`, with a working cleanup path; and `reauthenticate` succeeded with the real API key and left the connection working afterward (`test_connection` still succeeded).
- 2026-07-25: Fixed a session-expiry bug reported by the user as three seemingly separate symptoms (Odoo connection "disappearing," the Test connection button vanishing, "could not validate credentials" on save/test) — all traced to one root cause: an expired JWT wasn't detected anywhere, so pages silently rendered as if nothing was configured instead of prompting re-login. Added a client-side `exp`-claim check (`hasValidSession()`) used by `RequireAuth`/`NavBar` to redirect before any doomed API call, plus a centralized 401 handler in the API client that clears the session and redirects for anything the client-side check can't catch. Also extended `JWT_EXPIRE_MINUTES` from 60 to 10080 (7 days) per the user's request for production. Verified live: re-saved the user's Odoo API key (which they'd suspected was invalid) and it connected successfully on the first try under a valid session — confirming the credential was never the problem.

- 2026-07-25: Odoo version detection + version-aware field mapping registry — `POST .../credentials/test` now calls Odoo's public `common.version()` on every check (not just once), persisting server_version/server_version_major/server_serie/protocol_version on the tenant's credential and flagging `version_change_detected` (logged, not silently overwritten) when the major version changes between checks; new `app/odoo_mappings/` package (one file per integrated model: stock_picking, stock_warehouse, stock_picking_type, fleet_vehicle, hr_employee, res_partner) with `resolve_field(model, logical_name, version_major)` — version-specific overrides win when present, otherwise falls back to a `"default"` block, including for versions never seen before; every version block is currently empty since no real per-version field difference has been confirmed yet (none guessed at, per DECISIONS.md); graceful optional-field handling consolidated into `resolve_optional_field` (replaces the one-off shipping_weight-only check); picking enrichment, operation-type sync, warehouse sync, and fleet/employee lookup all now resolve field names through the registry instead of hardcoded strings — behavior is unchanged today (confirmed by the full existing test suite passing unmodified) since every default equals what was already hardcoded; Connection page shows the detected Odoo version and a warning banner on a detected version change. 88 backend tests passing. Verified end-to-end against the real Odoo instance: correctly detected "19.0+e" (major 19, matching what this whole project has been built and tested against), and a simulated stale-version scenario correctly flagged `version_change_detected` then settled back to false on the next check; operation-type refresh and a full planning run re-verified working end-to-end through the new field-resolution wiring, not just in isolation against a fake client.

- 2026-07-25: Vehicle and Driver management — new `vehicles`/`drivers` tables, locally-owned (no Odoo link required to exist); full CRUD with delete guards (vehicle blocked if a driver references it, driver blocked while active — see DECISIONS.md); optional, browse-only linking to Odoo `fleet.vehicle`/`hr.employee` that never overwrites local fields and gracefully returns `available:false` when the Fleet/HR module isn't installed; new `odoo_link_status="stale"` state — a linked record that disappears from a later Odoo browse gets flagged stale (not silently unlinked) and self-heals back to `linked` if it reappears; Vehicles/Drivers screens with create/edit forms and an Odoo-link picker. 62 backend tests passing. Verified end-to-end against the real Odoo instance: both Fleet and HR modules present (6 real vehicles, 29 real employees), linked real records, both delete guards triggered correctly, and the full stale→self-heal cycle confirmed live by linking to a nonexistent Odoo id and then a real one.
- 2026-07-25: Odoo sync work — addresses restructured into a shared split shape (street/street2/city/state_id+name/country_id+name/zip) used by both pickings and warehouses; new operation-type and warehouse sync config (`synced_operation_types`/`synced_warehouses` tables, refresh + toggle endpoints, "Resync List" screens — refresh always preserves existing `is_synced` toggles, unit-tested against a real SQLite session); stock.picking sync now only pulls pickings whose operation type is marked synced (empty selection = sync nothing); picking sync enriched with state, scheduled_date, resolved warehouse, origin, native weight, and an optional shipping_weight that degrades gracefully to `null` when the `delivery` module isn't installed (checked via Odoo's `fields_get`, no error); every fetched picking now persists to a new local `synced_pickings` table as a side effect of `/planning/run`; planner results table shows the new fields. 38 backend tests passing, no custom Odoo fields added anywhere (per DECISIONS.md). Re-verified end-to-end against the real multi-company Odoo instance: 86 real operation types across 9 warehouses (including a `code` value, `repair_operation`, not originally anticipated), toggling one operation type + warehouse on correctly scoped the next planning run to just that operation type's pickings, and `weight`/`shipping_weight` both came back with real nonzero values (this instance has the `delivery` module installed).
- 2026-07-25: Password show/hide toggle on login; multi-company support (tenant credential gets a selectable Odoo `res.company`, `allowed_company_ids` threaded through every XML-RPC read, new `GET/PUT .../credentials/companies|company` endpoints, company selector UI — see DECISIONS.md); planning results now carry customer name, items summary, and a broken-down address per stop instead of just the picking ID. Verified end-to-end against a real, multi-company Odoo 19 instance (`edu-accounting-learning.odoo.com`): company listing, company-scoped planning run (29 vs. 37 unscoped pickings, confirming the scoping actually filters), and item/address enrichment all confirmed against live data.
