# Changelog

One line per significant chunk of work, newest first.

- 2026-07-25: Added two more ways to move pickings on the Load Planning board on top of the existing single-card drag: dragging a whole compass-cluster header, and multi-select drag. The reducer's `MOVE_ITEMS` action already took `pickingIds: string[]` from the previous phase, so no shape change was needed — only the drag handlers needed to resolve a bigger array in more cases, which they now do once in `onDragStart` (reused for both the `DragOverlay` content and the eventual dispatch): a cluster header's drag carries every id from `clusterDestinations`'s *output* data (not the DOM, so a collapsed cluster still drags its full membership), a card that's part of the active selection carries the whole selection, and anything else carries just itself (a stale selection elsewhere is ignored, per spec). `DragOverlay` shows a `Badge`-based "N items" preview instead of a single card whenever more than one id is being dragged. Selection: a checkbox on each card toggles just that card; a plain click elsewhere on the card replaces the selection with only that card; ctrl/cmd-click toggles the same as the checkbox — documented as the explicit interaction model in design.md, chosen over ctrl/cmd-click alone because the board is a desktop-and-tablet tool and touch has no modifier-click. Selected cards get `border-accent bg-accent/5`, deliberately not the `ring-2 ring-accent` already used for a droppable's drag-over state, keeping the two visually distinct as required — and, like the drag-over ring before it, implemented as a class swap rather than a layered utility to avoid the same Tailwind-without-`tailwind-merge` override-order problem. A successful move now always clears `selectedIds` as part of the same state update rather than needing a second dispatch. Shift-click range-select skipped, as the task allowed. `tsc -b`, `vite build`, `eslint` all clean; verified via the built bundle (the new preview/selection strings present, bundle size increase consistent with the added code) since no browser automation tool is available in this environment.
- 2026-07-25: Wired up `@dnd-kit/core` so a picking card can be dragged from the Load Planning board's unassigned list into a vehicle, or between vehicles — the core mechanic, no cluster/multi-select dragging yet. `@dnd-kit/utilities` was skipped (not needed: the original card just dims via `isDragging` rather than being transform-followed, and `DragOverlay` positions its own floating copy on its own); `@dnd-kit/sortable` deliberately not installed (within-vehicle reordering is a later phase). A single `DndContext` wraps the board with `PointerSensor` (8px `activationConstraint` distance, so a tap doesn't get mistaken for a drag) and `KeyboardSensor` (keyboard-operable dragging, matching the accessibility floor from the design-system phase). Each picking row is `useDraggable`; the unassigned panel and each vehicle `Card` are `useDroppable`, with a `ring-2 ring-accent` drag-over indicator — deliberately a ring rather than a second `border-*`/`bg-*` utility, since this project doesn't use `tailwind-merge` and two utilities touching the same CSS property have an unpredictable winner based on Tailwind's generated stylesheet order, not DOM class order. New reducer action `MOVE_ITEMS` takes `pickingIds: string[]` (always a single-element array today) rather than a single-id shape, so a later multi-select phase can move several pickings in one dispatch without a new action type; it resolves the source container from `data.current.containerId` attached to each draggable and appends moved pickings to the end of the destination array (manual re-sequencing is a later feature, not inferred here). Dropping a card back into its own container is a no-op with zero state churn, checked both before dispatch (component skips it entirely) and inside the reducer itself (returns the identical state reference so `useReducer` bails out of re-rendering, not just a shallow-equal new object). `components/ui/Card.tsx` now forwards its ref (`forwardRef`) so `useDroppable`/`useDraggable` can attach to it directly — confirmed this doesn't change any existing consumer's usage. Capacity bars were confirmed to update automatically as a consequence of the state change alone, with no new capacity-calculation logic added. `tsc -b`, `vite build`, `eslint` all clean; verified via the built bundle (dnd-kit code and the `MOVE_ITEMS` action both present, ~45KB size increase consistent with `@dnd-kit/core`) since no browser automation tool is available in this environment to click-test the actual drag gesture.
- 2026-07-25: Built the static (non-drag) layout of the Load Planning board at `/load-planning` — the visual structure and state shape a later drag-and-drop phase will attach behavior to, with no dnd-kit and no real API calls yet. Board state (`unassigned: Picking[]`, `vehicles: Record<vehicleId, Picking[]>`, `selectedIds: Set<string>`) lives in a page-level `useReducer` with one stubbed `SELECT_ITEM` action. Confirmed and reused the FILO convention already established for `RouteStop.stop_order`/`backend/app/services/planning/filo.py::sequence_filo`: array index 0 = first delivered = last loaded. Added `frontend/src/lib/clustering.ts` (`getDistanceKm`/`getBearing`/`getCompassDirection`/`clusterDestinations`) — despite the task brief describing this as already existing, a full search of the repo turned up nothing, so it was built fresh, porting the haversine formula from `backend/app/services/planning/haversine.py` so on-screen distances agree with the backend's. Left panel (`UnassignedPanel`) groups unassigned pickings into collapsible sections by compass direction (8-point), each showing direction/count/distance-range and sorted by distance ascending; right side (`VehicleCard`, one per vehicle) shows two `CapacityBar`s (weight, volume — a vehicle can be full on one axis and empty on the other, so one bar can't represent both) and a numbered FILO stop list, both built on the existing `Card`/`CapacityBar` base components rather than new ad hoc styles. Layout stacks below Tailwind's `lg` breakpoint, matching the only breakpoint convention already in use elsewhere in the app. Both empty states are handled explicitly (zero unassigned, zero pickings on a vehicle), not left to render nothing. Mock data (`frontend/src/loadPlanning/fixtures.ts`, 10 pickings across 4-6 compass directions, 3 vehicles) is deliberately isolated from the components so a later phase can swap in a real API call by replacing one function. `tsc -b`, `vite build`, and `eslint` all clean; fixture distances/bearings cross-checked independently in Python against the same haversine/bearing formulas before trusting the on-screen clusters.
- 2026-07-25: Adopted Tailwind CSS v4 (`@tailwindcss/vite`, CSS-first `@theme` config — no `tailwind.config.ts`) as the styling approach, explicitly without a component library: every base component (`Button`, `Input`, `Select`, `Card`, `Badge`, `CapacityBar`, `Table`/`TableHead`/`TableBody`/`TableRow`/`Th`/`Td`, all in `frontend/src/components/ui/`) is hand-written, applying Tailwind utility classes internally. Design tokens defined once in `frontend/src/index.css`: a cool slate-gray neutral palette (background/surface/text/text-muted/border), a single restrained blue accent, and a three-color status scale (ok/warning/full) for capacity indicators, kept hue-distinct from the accent — chosen specifically to avoid the cream+terracotta, near-black+neon, and hairline-broadsheet "AI-generated" defaults, in favor of density and scanability for a dispatcher tool used all day. One radius (`rounded-md`) and one shadow (`shadow-sm`) used everywhere, no per-component exceptions. Every existing screen (Login, Connection, Operation Types, Warehouses, Vehicles, Drivers, Planning, NavBar) restyled onto the new components — the old hand-rolled `index.css` classes are gone, none remain referenced anywhere. Accessibility floor: every interactive element carries a `focus-visible:ring-2 focus-visible:ring-accent` treatment, every CSS transition has a `motion-reduce:` guard, and every color pairing's WCAG contrast ratio was computed and checked (all text/status pairings clear 4.5:1, most well past it — see `design.md` for the full table and the one documented tradeoff, the `border` token, which is deliberately lighter than the 3:1 non-text guideline to avoid a heavy-grid look). `design.md` added at the project root as the living reference for tokens, components, and rationale, with a dated decisions log. `tsc -b`, `vite build`, and `eslint` all clean; no interactive browser verification was possible in this environment (no browser automation tool available), so the rendered UI itself is unverified beyond the type-checked build.

- 2026-07-25: Fixed a session-expiry bug reported by the user as three seemingly separate symptoms (Odoo connection "disappearing," the Test connection button vanishing, "could not validate credentials" on save/test) — all traced to one root cause: an expired JWT wasn't detected anywhere, so pages silently rendered as if nothing was configured instead of prompting re-login. Added a client-side `exp`-claim check (`hasValidSession()`) used by `RequireAuth`/`NavBar` to redirect before any doomed API call, plus a centralized 401 handler in the API client that clears the session and redirects for anything the client-side check can't catch. Also extended `JWT_EXPIRE_MINUTES` from 60 to 10080 (7 days) per the user's request for production. Verified live: re-saved the user's Odoo API key (which they'd suspected was invalid) and it connected successfully on the first try under a valid session — confirming the credential was never the problem.
